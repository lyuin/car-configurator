# 3D化の描画スタイル 合意メモ

全11タスク完了後に出た「もっとゲームみたいな3Dモデリングで可愛らしい先進UIにしたい」という
方向転換について、モックで認識合わせをした結果。**実装は未着手。**

関連: [PLAN.md](PLAN.md)（2D版のここまでの経緯と決定事項）

## 大方針

3D表示にして、ゲームらしい可愛さと先進的な見た目を狙う。
ただし**寸法の正確さは一切犠牲にしない**。この道具の価値は「指定した寸法どおりの形が出る」ことなので、
見た目のためにプロポーションを誇張することはしない。

可愛さは プロポーションの誇張ではなく、**カメラ・質感・動き**で出す。

## 描画スタイル（合意済み）

### ボディ: 面は粗く、濃淡は光で決める

ローポリ（面を粗く、角をはっきり）を基本とする。ただし**面ごとに濃淡をランダムに振らない**。
光源を左上手前に固定し、面の向きで明るさを決める（セルシェーディング）。

| 部位 | 明るさ |
|---|---|
| 上面（ボンネット・ルーフ・トランク） | 最も明るい |
| 前面 | 中間（やや明） |
| 近側の側面（ベルトライン上） | 中間 |
| 近側の側面（下部・クラッディング以下） | 暗く落とす |
| 遠側の側面 | 最も暗い |

面ごとにランダムな色を置くとパッチワークに見える。光で決めると面が粗いままでも塊として見え、
**回したときに明暗の帯が面を順番に流れる**のでローポリの気持ちよさが出る。

下部を暗く落とすのは、車体を板ではなく塊に見せるため。

### タイヤとリム: ここだけなめらか

タイヤは丸く見えないと違和感が出る唯一のパーツなので、ボディと違ってなめらかに扱う。
- タイヤ: 放射グラデーション（左上が明るい）
- リム: メタリックな線形グラデーション + 明るいハイライトの弧を1本
- ボディの粗い面との**対比**が効くので、むしろ両方を混ぜる方が良い

### 輪郭線: シルエットと稜線だけ、細く

- 外周（シルエット）: 画面上で約 1.5px の濃い線
- 主要な稜線（折れ角が大きいところ）: 同じ太さで透かして入れる
- **面の境界すべてには引かない。** 全部に引くとワイヤーフレームに見える
- 太さは画面ピクセル固定にする。2D版で `vectorEffect="non-scaling-stroke"` にしたのと同じ考え方で、
  車の大きさによって線の太さが変わってはいけない

**輪郭線は2台比較のために必須。** 輪郭が無いと重ねたときにどちらの線か分からなくなる。
これがソフトシェーディング案（モックC）を採らなかった最大の理由。

### 仕上げ

- **リムライト**: 上端のエッジだけに細い明線を入れる。これだけで立体感と高級感が出る
- **接地影**: タイヤの下に小さく濃い影 + 車体全体の下に広く薄い影。浮かずに地面に乗って見える
- **エッジの面取り**: ボディのエッジを数mm分だけ斜めに削ると、そこに光が乗って細い明線になる。
  紙を折った見た目から、樹脂成形のミニカーの見た目に変わる

## 採用しなかった案

### チョロQ風のデフォルメ（却下）

「デフォルメ度スライダー」を提案した。0% で寸法どおり、上げるとタイヤが膨らみ全長が詰まって
チョロQに近づく、という可逆的な変形（寸法データ自体は変えない）。

**却下。** 理由は、デフォルメを上げると全長 4,575 と 4,885 の差が見た目で圧縮されて
比較の価値が落ちること。「可愛く眺めるモード」と「正確に比べるモード」を分けるより、
最初から寸法どおりで可愛く見える方向に振る方が筋が良いと判断した。

結果として、**可愛さはカメラ・質感・動きで出す**ことになった。

### ソフトシェーディング（モックC・却下）

一番「先進的」に見えるが、輪郭が無いので2台を重ねると見分けにくい。描画も重い。

### 面ごとにランダムな濃淡（モックB・改良して採用）

パッチワークに見えたので、光の向きで決める方式に変えた。

## 追加で採用するアイデア

| 内容 | 効果 | 備考 |
|---|---|---|
| **広角・低位置カメラ** | 手前のタイヤが大きく車体が詰まって見える | 実際の投影なのでデータは歪まない。実装が軽く効果が大きい。デフォルメを却下した今、**可愛さの主役** |
| **エッジの面取り** | 樹脂成形っぽい質感 | 上記「仕上げ」参照 |
| **車体色のパレット** | 愛着が出る。比較時の見分けにも効く | パステル6色程度。比較時は車Aが選択色・車Bが補色 |
| **寸法変更時のバネアニメーション** | ゲームの手触り | 数値変更で車がにゅっと伸びる。プリセット切替で形がモーフ。デフォルメを入れないぶん、動きで可愛さを稼ぐ |

## 既存コードの流用範囲

**そのまま使える（レンダリングに依存しない）**
- `src/domain/resolve.ts` 自動補完とロック
- `src/domain/ratios.ts` シルエット別の比率テーブル
- `src/domain/tire.ts` タイヤ規格のパース
- `src/domain/presets.ts` プリセット30台
- `src/domain/specTable.ts` 差分つきスペック表
- `src/state/` 全部（ロック操作・URL コーデック・localStorage）

**3D化で置き換わる**
- `src/domain/geometry.ts` の 2D ジオメトリ生成
- `src/components/CarSvg.tsx`

**重要**: `src/domain/profiles.ts` の `SIDE_PROFILES`（側面の輪郭）と `TOP_PROFILES`（上面の輪郭）は、
**2つの輪郭の間をロフト（補間）すれば3Dボディになる**。いまのデータから寸法を全部反映した立体が作れる。
しかも輪郭が点列なので、生成される面は自然に粗い多面体になる ＝ ローポリ方針と噛み合う。

## 技術的な前提

- three.js（react-three-fiber）で gzip +150KB 程度。合計 230KB 前後。iPad の性能では問題ない規模
- テストは3D部分でスナップショットが効かない。ジオメトリ生成の検証（頂点数、寸法が正しく反映されているか、
  車軸位置がフロントオーバーハングと一致するか等）に寄せる。2D版で「座標のテストは通るが図は破綻していた」
  を2度踏んでいるので、**画像での目視確認の手順は3Dでも必須**
- 寸法線と数値ラベルは2D版の方が明らかに読みやすい。3Dに寸法線を持ち込むか、
  2Dを「寸法モード」として残すかは未決定（下記）

## プロトタイプの結果（実装済み・合格）

「まず3D描画だけ実装して見た目を確認する」方針で試作し、**だいたいOKの評価を得た。**

実装したもの
- `src/domain/mesh.ts` — 寸法から3Dボディを生成。three.js に依存しない純粋なデータ
- `src/components/Car3D.tsx` — 合意したスタイルの描画。遅延読み込み
- App の「3D（試作）」トグル。**評価用なので URL には入れずローカル状態のみ**

形状生成の実際
- `SIDE_PROFILES`（上面の輪郭）と `TOP_PROFILES`（半幅）をステーションごとに補間してロフト。
  **狙いどおり既存データがそのまま使えた**
- ステーションは2つのプロファイルの折れ点の和集合。面の割れ目が輪郭の特徴点と一致し、
  面数70前後の自然なローポリになる
- 断面は8頂点（ルーフ絞り・ショルダー・ロッカー・フロア絞りの面取り）
- **面の頂点順は計算で外向きに揃える。** 手で巻き方向を揃えるとミスが出て、内向きの面が混ざると
  フラットシェーディングで黒い面が現れる。法線が重心から外を向いていなければ順序を反転させ、
  全シルエットでテストする

描画の実際
- `MeshToonMaterial` + 3段の `DataTexture` グラデーションマップで明暗を量子化
- `EdgesGeometry` の折れ角しきい値 16度でシルエットと稜線だけに線を出す
- タイヤ・リムは分割28/24のシリンダーでなめらかに
- 光源は左上手前、背後から弱い光でリムライト、床は `shadowMaterial` で影だけ受ける
- カメラは fov 46 の広角・低位置。ドラッグで回転し、離すと慣性で減衰

### 3D化で判明した修正

**バンパーの下端が絞られていなかった。** 前端から後端までシル高でフラットだと、鼻先が板のように
見えて3Dで破綻する。前後端の断面だけ下端を断面高さの 22% 持ち上げて解決。
2D側面図では単なる直線だったので見えなかった問題。寸法（全長・全幅・全高・シル高）は変わらない。

### バンドルへの影響

three.js は遅延読み込みにした。別チャンク（gzip 244KB）になり、3Dを開くまで読み込まれない。
**メインバンドルは 82.68KB のまま変わらない。**

### 目視確認について

2D版では SVG を書き出して `qlmanage` で PNG 化していたが、3Dは WebGL なのでこの手が使えない。
代わりに、メッシュを SVG に投影するオフラインレンダラ（ペインターズアルゴリズム + フラット
シェーディング）を一時テストとして書いて確認した。

ただし**この方法には限界がある**。車体全長にわたる大きな床面を小さな側面より手前に誤判定し、
実際には存在しない「前方に突き出した板」が見えた。数値を出して2Dプロファイルと突き合わせた結果、
メッシュ自体は正しいと確認できた。three.js の深度バッファでは起きない。
形状の最終判断は実機のブラウザで行うのが確実。
